# Changelog

and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- Initial package scaffold: CLI with --help and --version.
- Format schemas and pure parsers for `spec.md`, `testplan.yaml`, `bindings.yaml`, `triage.json`, `questions.json`, `.spec-gate/config.yaml`, `.spec-gate/commands.yaml` and evidence envelopes, with the field-to-layer table, the per-kind required fields, ID and source-line ID handling, the reference-state table and the evidence phase rules, documented in `docs/formats.md`.
- `spec-gate digest <spec-dir> [--repo <path>]`: a deterministic `sha256:` digest of the normative layer of a spec, frontmatter `id` included (canonical JSON per RFC 8785, whitespace normalised in prose fields only, `commands_ref` a full commit ID and the referenced argv lists read from git at that commit, from a regular file at the repository root only; `input`, `steps`, `environment` and `verifier` are kept exactly), with golden fixtures and the rules in `docs/digest.md`.
- `triage` verb: derives the triage class from `triage.json` with a versioned truth table in `src/triage/`, writes `class` and `rule_version` back through a temporary file renamed into place, keeping the file's permission bits and never removing a path it did not create (a symlink, or a file or directory that cannot be written, is refused with a named error), and reports the class, the deciding row, every unknown field of the precedence rows when an unknown forces `clarify`, and the spec profile; the rule is documented in `docs/triage.md`.
- `intake file` CLI verb: create `specs/<id>/source/` in the target repository from a local file with `base_commit` and `commands_ref` read from the remote default branch, a secret scan before anything is written, optional attachments and `--no-raw`, and a `--check` drift mode.
- `spec-gate lint <spec-dir> [--strict] [--final] [--profile <light|full>] [--config <path>]` and `lint-ack`: a deterministic JSON report (`spec-gate-lint/1`, findings sorted, nothing machine-local) over a rule registry with profiles and status gating, a git-free loader that refuses links, non-regular files, files over 4 MiB and non-UTF-8 text and turns every format error into a finding, the profile taken from `triage.json` (in-memory derivation, `--profile` only as a fallback), `acks.yaml` for acknowledged warnings with an atomic append writer, a `skipped` list naming the rules a run did not evaluate and why, and the form rules for one GOAL, AC coverage by a test-plan row and non-empty Non-goals; documented in `docs/lint.md`. Fifteen content rules run in the full profile: DF coverage, covers and binding references, source-ledger completeness and references, `owner: none`, open residuals and blocking questions gated on `proposed`, DC answers and checkable provenance, retired IDs still in use, vague words in normative text, an unanswered-question budget settable through `--config` (config findings name `config:<basename>`, never the caller's path), and the freshness of `triage.json`, checked in both profiles, whose stored class never picks the profile. Reference states are checked against git with `--repo`, `--default-ref` and `--base` (offline, read-only, a scrubbed git environment, regular files only at a commit): `base_commit` and `commands_ref` must equal their `source/meta.json` copies and be ancestors of the reference commit, a spec change under `.spec-gate/` is an error, every `static` row must name a command of the set at `commands_ref`, `.spec-gate/config.yaml` is read at the reference commit, and under `--final` an error rule skipped for no git or an absent input is itself an error (`rule-skipped`). The repository is the one `--repo` names (required with `--default-ref` or `--base`, never discovered from the spec directory), `--base` must lie on the `--default-ref` branch when both are given, and a spec change under `.spec-gate/` is matched without regard to the case of its first path component.
- `spec-gate propose` and `spec-gate bind` with `bindings.log`: `propose` needs git inputs, a spec directory that is `specs/<name>` (exactly one level below the top-level `specs/`), a `draft` status, no existing log and a work tree whose `spec.md` and `bindings.yaml` are the files at `HEAD`, runs the final lint in process (findings exit 1 and write nothing), then sets `status: proposed` alone (the digest stays the same) and records the propose commit and the hash of the committed `bindings.yaml`; `bind` changes one existing binding of a proposed spec within the rule of its row's kind, appending the full binding to a hash-chained log and rewriting `bindings.yaml`. The new lint rule `bindings-log` (gated, needs git) checks the log's sequence, shape and chain, that the propose commit is an ancestor of `HEAD`, the hash of `bindings.yaml` read from git at that commit, that the spec was a draft without a log at the propose commit, that no bind entry adds an ID or breaks its row's kind rule, that the replay equals `bindings.yaml`, that the spec directory is `specs/<name>` (`spec-off-layout` anywhere else, at `proposed` and under `--final`), that a log the diff base holds in `specs/` for a spec of the same id is never rewritten or removed, and that a proposed spec does not leave its directory; `binding-status` accepts a red-first row at `existing` once `bindings.log` holds a bind entry for it. Exit codes follow `lint` and `lint-ack` (0 written, 1 findings, 2 refusal); the log format is documented in `docs/formats.md`, the verbs and the rule in `docs/lint.md`.
- `spec-gate export <spec-dir> --format ow --repo <dir> --default-ref <ref>` and `spec-gate export <spec-dir> --check <slicer-return.yaml>`: the first prints the deterministic `ow` slicer briefing of a proposed spec (fixed key order, byte-identical across runs: pinned `spec_ref` and digest, goal, qualified AC and TP strings, test-plan rows, Non-goal paths and behaviour lines, relevant docs, allowed-changes hint), refusing unless the work-tree `spec.md`, `testplan.yaml` and `bindings.yaml` are byte-equal to the regular-file blobs at the `--default-ref` commit, read offline through the hardened git layer, with `status: proposed`; the second checks that every qualified AC and TP id of the spec appears as a whole token in a string field of at least one task of a slicer return, exiting 1 with the missing ids in file order. No entry of `allowed_changes_hint` is covered by an entry of `forbidden_changes` (a Non-goal path, the spec's `spec.md` and `testplan.yaml`; an entry covers a candidate it matches or lies above, with `*` and `**` as the only glob syntax), and a binding or Non-goal path the rule cannot judge is refused by name (`binding-path-not-canonical`, `binding-path-glob`, `nongoal-path-not-canonical`, `nongoal-glob-unsupported`). Exit codes follow `lint` (0 result, 1 missing ids, 2 usage and every refusal with a named error); documented in `docs/export.md`, the code lives in `src/exporters/`.
- Approval check as a library: a `HostAdapter` interface in `src/host/` for the facts a code host supplies (the pull request, its reviews, review enforcement for `specs/` and `.spec-gate/`, the last change under `.spec-gate/`, and a CI run status for later evidence checks), and `checkApproval` in `src/approve/`, which returns a deterministic report (`spec-gate-approve/1`) with one entry per condition: an approving review that stands on the head commit (the latest decisive review per account, a later request for changes or dismissal cancels it), an approver from `approvers` who is neither the author nor an agent identity (logins compared without regard to case, settings read from git at the tip of the default branch, with or without a base commit), the digest at the head equal to the digest at the commit of the approving review, `status: proposed` with a clean final lint of exactly the head's spec directory, agent identities configured and separate from approvers (`approval-not-verifiable` otherwise), review enforcement for both paths (`approval-not-enforced` otherwise, `unknown` counts as not enforced) and no change under `.spec-gate/`. `approved` is true only when all hold; `approve_reported` marks an approve that is not verifiable or not enforced; a host method that throws or returns an unexpected value fails its conditions with `host-failed`. The verb that runs it, an eighth condition and the diff base of conditions 7 and 8 are in the `spec-gate approve-check` entry under "Security". Described in `docs/approve.md`.
- `spec-gate questions`, `answer` and `status`: `questions` prints one JSON line (`spec-gate-questions/1`) listing a spec's unanswered questions in numeric ID order (the frontier, since the format has no field by which one question depends on another) with their counts, exiting 0 with none unanswered and 1 with one listed; `answer` is the only verb that writes an answer, appending one to a draft spec's `questions.json` (through the same hardened reader and an atomic replace that keeps the file's permission bits) with the answer and chosen option label (from `--answer`/`--option` or, for `--accept-recommended`, the question's `recommended` label, never the first option), the channel, the author and an optional `https:` comment URL recorded as provenance and the `time` taken from a clock seam with no flag or environment override, serialising the file deterministically (fixed key order, two-space JSON, trailing newline, `parseQuestions` of the text deep-equal to the document); `status` prints one offline JSON line (`spec-gate-status/1`) with the spec's status, triage class stored and derived, question counts, open residuals, bindings by status and rows without a binding, the `bindings.log` entry count and propose commit, and the ack count, reporting a file that does not load as `null` with its code in an `errors` list. Every file is read through the lint's hardened reader (a link, a non-regular file, a file over 4 MiB or non-UTF-8 text is a named error). Exit codes follow `lint` and `lint-ack` (`questions` 0/1, `answer` 0 when written, `status` 0 for a report, all 2 for a usage error or refusal). Documented in `docs/questions.md`, the code lives in `src/state/`.
- Evidence layout, the `commands_digest` definition and four evidence lint rules: envelopes live in `specs/<id>/evidence/`, one `TP-<n>.jsonl` (JSON Lines, both phases) per test-plan row, the file name the mapping from an envelope to its row; a regular file there whose name is not a row file is a `format` finding (`evidence-layout`), a link, subdirectory or other non-regular entry is a `file` finding, and the directory is parsed envelope by envelope as an optional lint input. `commands_digest` is defined as `expectedCommandsDigest`: SHA-256 over the JSON serialization of the list of a run's argv lists, the same bytes the reference runner hashes; a spec-gate check is a run of one command, so the list holds the row's one command template read at `commands_ref` with a `{selector}` placeholder left unsubstituted. The rules, registered after `bindings-log` and full-profile only: `stale-evidence` (warning, needs git, acknowledgeable with the row ID or ID `commands`) judges every `baseline` envelope on five causes (commit not `base_commit`, `dirty`, a `commands_digest` that is not the digest of the row's one command at `commands_ref`, read there and never at the default tip, an unreadable command set reporting once with id `commands` and judging no digest, a selector that is not the row's binding selector, and `command-unknown`: a row whose command cannot be determined (not static with no selector in its binding, or selector-bound while no command of the set carries the `{selector}` placeholder) never passes the digest unjudged; `closure` envelopes are never stale); `unproven` (warning) needs a fresh passing `baseline` envelope for every `stays-green` row, judging the fields the envelope carries itself; `self-reported` (warning) flags a row whose file holds a `producer: local` envelope (`host` is not flagged, `ci` is judged by the closing check); `evidence-unknown-row` (error) refuses a well-named file for an unknown TP ID. Documented in `docs/lint.md` and `docs/formats.md`.
- `createGitHubHost` in `src/host/github.ts`: a `HostAdapter` for GitHub over the REST API (version `2022-11-28`), read-only and without a new dependency. It maps the pull request, every page of its reviews (a `PENDING` review is left out, an unknown state throws), the review enforcement of the target branch (`enforced` only when an active ruleset rule or a readable classic branch protection requires at least one approving review, a code-owner review alone is `not-enforced`, a source that answers 403 or 404 gives `unknown`) and the last change under `.spec-gate/` with the approver of the pull request that merged it (an approval of the merged head commit, given no later than the merge; `null` when that cannot be told). `ciRunStatus` now takes the commit and the run (`ciRunStatus(commit, run)`) and is `verified` only for a completed run of the same repository at that commit. The adapter fails closed: any other status, a redirect (never followed), a rate limit (named, never retried), a request over 10 seconds, a body over 4 MiB, invalid JSON, a mistyped field, a next link to another origin or path and a list of more than 30 pages throw an error that holds the method, the path and the status only. The token is sent as `Authorization: Bearer` to the API root alone, which must be `https:` unless it is a loopback host, and never appears in an error or a returned value. Described in `docs/approve.md` ("GitHub adapter").

### Security

- `intake file` hardening: the remote default branch is validated and fetched by its full `refs/heads/` name only (a tag of the same name, or a branch named like a git option, can no longer change `base_commit` or the local repository), git runs with a scrubbed environment in its own process group, `--remote` must be a configured remote and no error echoes a URL, the secret scan covers keywords inside identifiers, quoted keys, PGP key blocks and `ghr_` tokens and refuses UTF-16 and NUL input, writes are atomic and rolled back, and `--check` exits 2 on an error.
- `intake file` exits 2 on its own usage errors and unexpected exceptions (exit 1 belongs to `--check` drift alone), refuses a `specs` or `specs/<id>` that is already a symlink with `source-not-in-repo` before anything is written, and the fetch passes `--write-fetch-head` so a repo-local `fetch.writeFetchHEAD=false` cannot leave a stale FETCH_HEAD; the remote is trusted as configured (local-path URLs and `url.<base>.insteadOf` rewrites included), with integrity against the shared upstream deferred to lint.
- Every git call of `lint`, `digest` and `intake` is started with `safe.bareRepository=explicit`, `core.fsmonitor=false`, `core.hooksPath` set to the null device and (not for `intake`, which fetches) `protocol.allow=never`, with `GIT_GRAFT_FILE` set to the null device and (not for `intake`) `GIT_ALLOW_PROTOCOL` set to the empty string, so that no transport starts whatever the repository's `protocol.<name>.allow` says (these protections need git 2.38 or newer), and a git that is stopped by a signal is a `git-failed` error instead of a refusal; `digest` and `lint` use a repository only when the `.git` entry of its work tree (a directory or a `gitdir:` file, never a symbolic link) leads to the git directory git found and the common git directory is not inside the work tree, so a spec pull request cannot commit a git directory of its own while a linked worktree, also one inside a bare repository, is accepted, and `digest --repo` no longer accepts a bare repository or a git directory.
- `spec-gate repo-check --repo <dir> (--default-ref <ref> | --base <commit>)`: a repository-wide check, meant for every pull request, that no protected spec at the diff base disappears. Protected is every regular `spec.md` anywhere in the diff-base tree (ASCII case ignored, not only under `specs/`) that parses and is not a draft or has a sibling `bindings.log`; at `HEAD` the same path must hold a regular `spec.md` that parses (`spec-removed`, also when the spec turns up under another path), with the same id (`spec-id-changed`), not back at `draft` (`spec-status-reverted`) and with its log (`log-removed`). It closes the cases the per-spec lint cannot see: a deleted spec directory, a rename together with an id change, and a spec moved into `specs/` with a fresh log. Both trees are read from git, never from the work tree, through the lint's git input resolution and hardened runner; the listings are capped at 50000 entries and 4 MiB and the diff base at 1000 `spec.md` files (`tree-too-large` past a cap); the report is one JSON line (`spec-gate-repo-check/1`, findings sorted), exit 0 clean, 1 findings, 2 usage error; documented in `docs/lint.md`.
- `spec-gate approve-check <spec-dir> --repo <dir> --default-ref <ref> [--base <commit>] --github-repo <owner/name> --pr <number> [--api-url <url>]`: the approval check as a command for a pull request job. It makes the GitHub adapter, calls `checkApproval` and prints the report as one JSON line; it exits 0 only for a report that says approved, 1 for a report that does not (a host that fails or cannot be reached included) and 2 for a usage error, a refusal or an exception. The token is read from the environment variable `GITHUB_TOKEN` only: there is no option for it, an argument the verb does not know is refused without being repeated on stderr, no refusal repeats a value, and an output that would hold the token is withheld. The report (`spec-gate-approve/1`) has an eighth condition, `repo-check-clean`: the repository check runs from the merge base of the head with the default branch to the head, both read from git and never from the work tree, so a pull request that also deletes another protected spec, changes its id, puts it back to `draft` or removes its log is not approved (`repo-check-findings`, `tree-too-large`). The new report field `commands` lists the argv lists a runner may start for the spec (every command a test-plan row names and the `{selector}` command of the set), read from git at the spec's `commands_ref`, never at the tip of the default branch; it is `null` with the gap `commands-not-resolved` when they cannot be read, and never a condition. Conditions 4 (the final lint), 7 (`config-untouched`) and 8 measure from one base, the one merge base of the head and the tip of the default branch, and never from `--base`, which is only compared with the base the host reports and is no longer handed to the lint: a base the host reports can be older than a default commit the head has merged, and measured from it a settings file put back to its old text, a spec that commit added and the pull request deletes, or a merged `bindings.log` replaced through a second propose did not show. With more than one merge base the three conditions fail with the new code `ambiguous-merge-base` and nothing is measured from a pick. `--help` and `-h` among the arguments of the verb are refused with exit 2 (`spec-gate help approve-check` prints the help); `--version` and `-V` still exit 0, so a job also requires the JSON line with `approved: true`. Described in `docs/approve.md`.

### Fixed

- `bindings-log` after a squash or rebase merge: when the propose commit is not a commit or not an ancestor of `HEAD` and the diff base holds the log of the spec at the same path with the same propose entry, `bindings.yaml` read from git at the diff base is the anchor and only the bind entries after the merged log are checked (unknown ID, kind rule) and replayed over it (provided every TP ID the merged log binds still holds its last bound value there), so a merged spec passes on the default branch, in a fresh clone and in later bind pull requests; without such a log `propose-not-a-commit` and `propose-not-ancestor` stay errors.
- Format fields that hold an integer (`runs`, `baseline` and `threshold` of a measurement row, `questions.warn_above` in `config.yaml`, `rule_version` in `triage.json`, `exit` in an evidence envelope) now refuse a value outside the IEEE-754 safe range -(2^53-1) to 2^53-1, which YAML and JSON decode to a double so that two spellings of one big integer arrive equal; a big integer that must stay exact is written as a quoted string, which stays accepted.
- `export`, `lint` and the spec state verbs resolve `--repo` and the spec directory through the native realpath, so a spelling of either in another case on a case-insensitive file system is compared with the spelling on disk before the containment test; a spec directory that really lies outside the repository is still refused with the same `spec-dir-invalid` message.
