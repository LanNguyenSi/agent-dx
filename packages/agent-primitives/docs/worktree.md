# `worktree`

Creates, reports and removes linked git worktrees for task branches. Part of the [agent-primitives](../README.md) CLI. This page covers `worktree create`, `worktree remove` (with `--sync-main`), `worktree sweep` and `worktree list`; everything above the `## remove` heading documents `create`.

Before delegating a task, an orchestrator typically makes a worktree on a fresh branch, points it at the run directory, links the dependency directories that are too big to reinstall, and checks that the result runs. Done by hand that is a dozen commands, and each has a known way to go wrong: a relative path resolved against `git -C <repo>` puts the worktree inside the repository, a branch started from `origin/<default>` inherits that branch as its upstream (a bare `git push` then aims at the default branch), and the run pointer gets written where git does not ignore it. `worktree create` does the whole sequence, refuses what is unsafe, and reports everything a run record needs in one envelope.

```bash
agent-primitives worktree create --repo ~/src/app --branch fix/login --run ~/work/runs/login-fix
agent-primitives worktree create --repo ~/src/app --branch fix/login --base origin/develop \
  --path ~/wt/app-login --links-from ~/.config/app-links.txt \
  --setup 'composer dump-autoload' --smoke 'vendor/bin/phpunit --testsuite smoke' --pass-regex '^OK \('
```

## What it does

In this order:

1. Validates the options and every precondition below. A refusal changes nothing. A SIGINT or SIGTERM that arrived during this step ends the command here, and one that arrived during steps 2 and 3 ends it before step 4, with nothing created (see [Time bounds](#time-bounds)).
2. Fetches `origin` (unless `--no-fetch`). This updates remote-tracking refs only.
3. Resolves the base: `--base`, or `origin/<default branch>` (see Default base below).
4. Runs `git worktree add --no-track -b <branch> -- <path> <base>` from the main checkout.
5. Writes the `.ai/run` pointer (with `--run`), when git ignores that path.
6. Creates the dependency links and excludes them.
7. Runs `--setup`, then `--smoke`.

Steps 5 to 7 never undo the worktree: what did not work is reported in the envelope, and the worktree stays.

The main checkout is never switched, reset or stashed, and `git stash` is not used at all. Its HEAD, index, working tree and stash are the same before and after (the test suite asserts this on a checkout that has all four in use).

## Default base

Without `--base`, `worktree create`, `worktree remove` and `worktree list` use origin's default branch, resolved the same way in all three. The candidates, in order, are the target of `refs/remotes/origin/HEAD`, then `refs/remotes/origin/main`, then `refs/remotes/origin/master`. A candidate counts only when it passes the guard `remove --base` and `list --base` go through (`create --base` is unguarded): it is one exact, existing remote-tracking ref of the configured remote `origin`, a commit, and not a symbolic ref. So the `origin` remote has to be configured, and `origin/HEAD` is skipped (the next candidate is tried) when it points at a local branch, at a symbolic ref, at a ref of another remote or at a ref that does not exist. When no candidate passes there is no default base: `create` refuses with `default_branch_unresolved`, `list` reports `merged: unknown` with no `base`, and `remove` treats the merge state as unknown (`merge_state_unknown` under `--require-merged`; the unpushed check still applies, and `--delete-branch` of a branch with commits no remote branch holds is refused as unpushed).

Everything that decides whether work may be discarded or measured (`remove`'s merge check, `list`'s `ahead`, `behind` and `merged`) reads the candidate by its full name, `refs/remotes/origin/<branch>`, so a local branch or a tag called `origin/main` cannot stand in for it. What is shown, and what `create` starts the branch from, is git's own unambiguous abbreviation of that ref: `origin/main` in a normal layout, `remotes/origin/main` where a local branch or tag of the name `origin/main` exists, or the full `refs/remotes/origin/<branch>` when no shorter name is unambiguous. In a layout where even the full name is ambiguous (local refs spelled like it as well as like the shorter forms), `create` refuses with `worktree_add_failed` rather than start from a different ref. A fallback to `origin/main` or `origin/master` names its source as `origin/HEAD is not set or not usable`.

## Options

| Option | Meaning |
| --- | --- |
| `--branch <name>` | Required. The new branch. It must not exist yet. |
| `--repo <path>` | Repository to branch from. Defaults to the invocation directory (`-C`). May be the main checkout, a subdirectory, or a linked worktree; the main checkout is found through git. |
| `--base <rev>` | Start point of the branch: any revision that names a commit (`origin/develop`, a tag, a sha). Default: `origin/<default branch>`, the default base described under Default base below. An explicit local branch name is used as it is, not fetched ahead of time. |
| `--path <dir>` | Exact worktree directory. |
| `--root <dir>` | Directory to create `<branch>` in; the directory is named after the branch with every character outside `A-Za-z0-9._-` replaced by `-` (`feat/one` becomes `feat-one`). Exclusive with `--path`. |
| `--run <dir>` | Run directory. Its absolute path is written, followed by a newline, to `.ai/run` in the worktree, but only when `git check-ignore --no-index` says `.ai/run` is ignored there. The directory must exist. |
| `--link <rel>` | Repository-relative path to symlink from the main checkout into the worktree. Repeatable, and comma-separated values are split. |
| `--links-from <file>` | File with one link path per line; blank lines and `#` comments are ignored. It is operator configuration and must live outside the repository. Merged with `--link`; duplicates are made once. |
| `--setup <cmd>` | Shell command run in the worktree after the links exist (`sh -c`). A non-zero exit makes the result `fail`. |
| `--smoke <cmd>` | Readiness check run in the worktree after setup. Its result is `ready` or `not_ready`. Skipped, as `not_run`, when setup failed. |
| `--pass-regex <regex>` | With `--smoke`: the verdict comes from the pattern instead of the exit code, exactly as in [`verify`](verify.md): a match on the combined stdout and stderr is `ready` and no match is `not_ready`, whatever the exit code says. The pattern gets the `m` flag, so `^` and `$` anchor per line. A run that never concluded (timeout, exit 126 or 127, a kill) is `not_ready` and the pattern is not consulted. |
| `--no-fetch` | Do not fetch `origin`; branch from the refs as they are. |

Relative `--path`, `--root`, `--run`, `--links-from` and `--repo` values resolve against the invocation directory (`-C`, or the process directory), never against the repository. The reported worktree path is always absolute.

Defaults when neither `--path` nor `--root` is given: `<parent of the main checkout>/<repo>-worktrees/<branch dir>`.

The fetch has a fixed two-minute limit. `--setup` and `--smoke` have none; SIGINT and SIGTERM stop them.

## Links

Each link is a symlink at `<worktree>/<rel>` pointing at the absolute path `<main checkout>/<rel>`. A link entry must be relative, must not climb out with `..`, and must not be `.git` or below it; such an entry is a `link_invalid` refusal, before anything is created.

Per entry, after the worktree exists:

- The source must exist in the main checkout, else the entry is skipped as `source_missing`.
- The destination must not exist (`destination_exists`, for instance a tracked path) and no existing parent of it may be a symlink or a non-directory (`parent_is_symlink`, `parent_not_directory`), so nothing is ever written through one link into the main checkout. Missing parent directories are created.
- Once the link exists, git is asked whether it ignores the path (`git check-ignore --no-index`). If it does not, `/<rel>` (glob characters escaped) is appended to `info/exclude` of the repository's common git directory, which every worktree shares. A directory-only pattern such as `vendor/` does not cover a symlink, which git treats as a file, so the line is added in that case too.

The exclude line lives in the common git directory, not in the new worktree, so it also applies to the main checkout and stays in place after the worktree is removed.

### Link manifest

When at least one link was made, `create` records them in
`agent-primitives-links.json` inside the new worktree's git administration
directory (`<common git dir>/worktrees/<id>/`), never in the working tree: a
JSON object with `version` (`2`), `toolVersion` and `links`, each link
carrying its repository-relative `path`, the absolute `target` it points at,
`createdAt`, and the resolved identity of the target as `create` saw it
(`resolved`, its `realpath`, and its device and inode as `dev` and `ino`).
The file is created exclusively with mode 0600. [`probe`](probe.md) run in
that worktree reads it and treats each link that still stands as recorded
like a `--link`, so a plan from the run directory needs no extra flag; a
link that has been replaced or retargeted since, or whose target now leads
to a different directory (the main checkout swapped what the path resolves
to), is not trusted; the recorded device and inode may miss a directory
deleted and recreated at the same path where inode numbers are reused. The trust rule, the checks on the file (`O_NOFOLLOW`
where the platform supports it, owner and mode on POSIX only) and why it
lives outside the working tree are in probe.md under "Links recorded by
`worktree create`".

`git worktree remove` deletes the administration directory, and the manifest
with it. Nothing is written when no link was made. A failed write is a
warning and `links.manifest.status: "failed"`; the worktree and its links
stay, and `probe` then needs `--link` for them. A link whose path the
reader would reject (for example one containing a backslash) is still made
but left out of the manifest, listed under `links.manifest.unrecorded` with
a warning, and the other links are recorded as usual.

A link whose target does not resolve (a dangling symlink in the main
checkout) is made but not recorded either. It is listed under
`links.manifest.unrecorded` when the other links are written; when no link
can be recorded, the manifest status is `failed` and nothing is recorded.
Probe refuses a missing source, so create the target in the main checkout
first and then pass `--link`.

The result lists `links.made` (`path`, `target`, `exclude`: `added`, `already_ignored` or `failed`), `links.skipped` (`path`, `reason`, `detail`) and `links.manifest` (`status`: `written`, `not_needed` or `failed`, with `path` or `reason`, `unrecorded`: `path` and `reason` of each link left out of a written manifest, and `unresolved`: the same for links whose target does not resolve, on a `failed` manifest, where they are not part of `unrecorded`). When the writer fails while another link dangles, the warning separates the two remedies: pass `--link` for the links that resolve, create the target first for the dangling ones.

## Result

The usual [envelope](output-shape.md) with `command: "worktree create"`, plus:

| Field | Meaning |
| --- | --- |
| `worktree` | `path` (absolute), `branch`, `repo` (basename of the main checkout), `mainCheckout`, `head` (sha the worktree is at). |
| `base` | `ref` as passed to git, `sha`, `source` (`flag` or `default`), and for a default base `detail` naming where it was read from. |
| `fetch` | `status` `fetched` or `skipped`, with `reason` (`--no-fetch`, or no `origin` remote). |
| `upstream` | `null` when the branch tracks nothing, which is the expected value. A warning is added otherwise. |
| `runBase` | A ready-made line for a run record: `run-base[<repo>] = <sha>`. |
| `pointer` | `status` `written`, `skipped` (with `reason`) or `not_requested`, and the `path`. |
| `links` | `made` and `skipped`, as above. |
| `setup` | `status` `ok`, `failed` or `not_requested`, with `command`, `exitCode`, `timedOut`, `durationMs`, `logPath`; a failure adds `reason` and `outputTail`. |
| `smoke` | `status` `ready`, `not_ready`, `not_run` or `not_requested`, with the same fields and `passRegex` when set. |

`status` is `ok` (exit 0), or `fail` (exit 1) when setup failed or the smoke check is `not_ready`. In both cases the worktree exists.

## Refusals

A refusal is `status: "usage_error"` (exit 2) with a `reason`, a `message`, and for some reasons `details`. Nothing was created or changed, except that a `fetch_failed` or `worktree_add_failed` reports git's own failure (a git that did not finish in time is one such failure, see [Time bounds](#time-bounds)).

| `reason` | Cause |
| --- | --- |
| `not_a_git_repo` | `--repo` does not exist or is not inside a git working tree. |
| `bare_repository` | The repository is bare; there is no main checkout to branch from. |
| `branch_invalid` | The name is not a valid branch name. |
| `branch_exists` | The branch already exists. This command only creates branches. |
| `branch_checked_out` | The branch is checked out in a worktree (the main checkout included); the message and `details.worktree` name it. A stale entry is marked `prunable`. |
| `target_exists` | The target path exists, whatever it is. |
| `target_inside_checkout` | The target lies inside the main checkout, however its path is spelled (symlinks and letter case on a case-insensitive volume included). |
| `target_inside_worktree` | The target lies inside another working tree of the repository: the linked worktree `--repo` points into, or any registered worktree that git does not list as prunable (a locked entry counts even when its directory is missing). `details.worktree` names it. |
| `path_and_root_conflict` | Both `--path` and `--root` were given. |
| `base_not_found` | `--base` does not name a commit (or starts with `-`). |
| `default_branch_unresolved` | No `--base`, and `origin/HEAD` is not set or not usable and neither `origin/main` nor `origin/master` is a plain remote-tracking branch of `origin` (see Default base). Pass `--base`. |
| `fetch_failed` | `git fetch origin` failed, or did not finish within 2 minutes and was stopped. Pass `--no-fetch` to go on with the refs as they are. A repository with no `origin` remote skips the fetch with a warning instead. |
| `run_dir_missing` | `--run` is not an existing directory. |
| `link_invalid` | A link entry is unusable (see Links). |
| `links_file_unreadable` | `--links-from` cannot be read. |
| `links_file_inside_repo` | `--links-from` lies inside the repository, however its path is spelled (as for `target_inside_checkout`). |
| `option_invalid` | `--pass-regex` without `--smoke`, or an empty `--setup` / `--smoke`. |
| `worktree_add_failed` | `git worktree add` itself failed; the message carries git's error. When it did not finish in time and was stopped, the message says so and that the target, the branch and a lock file may exist in part: check `git worktree list` and run `git worktree prune` before trying again. When it failed for any other reason, the branch it had just created is deleted again only when no worktree has it checked out (the target included: `git worktree add` also exits non-zero when a post-checkout hook fails after the worktree exists, and then the worktree and its branch are kept) and it still points at the commit it started at; a branch that existed before the call is never deleted. The message says which of these happened: removed, kept because a worktree uses it (when a hook left that worktree on another branch or a detached HEAD, the message says so), kept because it moved, kept because the worktree list could not be read, or not removable (with git's reason and a hint to inspect it before deleting it by hand). A registration of the target whose directory was deleted before the add (an old prunable entry) does not count as a worktree this call created, so the new branch is removed; when it is the entry THIS call left that git lists as prunable (a failing post-checkout hook that deleted the new worktree's `.git`), the message says the worktree at the target was created but is now prunable, keeps the branch, and points at `git worktree prune`. |
| `git_timeout` | A git call that reads (`rev-parse`, `show-ref`, `for-each-ref`, `remote`, ...) did not finish within its bound and was stopped; the message and `details` (`git`, `boundMs`, `cwd`) name the call. Nothing was created. See [Time bounds](#time-bounds). |
| `interrupted` | A program that calls `createWorktree` itself passed a `signal` that was aborted (SIGINT, SIGTERM) by the time the command reached the fetch or `git worktree add`. Neither the worktree nor the branch was made. The CLI never reports it: on these signals it ends at the same points with exit 130 or 143 and no output. See [Time bounds](#time-bounds). |

## remove

```bash
agent-primitives worktree remove ~/wt/app-login
agent-primitives worktree remove ~/wt/app-login --delete-branch --require-merged
agent-primitives worktree remove --path ~/wt/app-login
```

The worktree to remove, as one positional `<path>` or with `--path <dir>` (the flag `worktree create` takes). A relative value resolves against the invocation directory (`-C`), never against the repository. Both forms together must resolve to the same path (compared after resolving against the invocation directory, without following symlinks), otherwise the command refuses with `option_invalid`; neither form is `option_invalid` too.

| Option | Meaning |
| --- | --- |
| `--path <dir>` | The worktree to remove, as an alternative to the positional `<path>`. |
| `--force` | Remove the worktree even when it is dirty (a tracked file flagged assume-unchanged or skip-worktree that is present in the work tree included, edited or not, since git status does not show edits to it), has commits no remote branch has, is locked, holds a nested worktree or submodules, a check could not be made (`status_unknown`, the flagged files, `unpushed_state_unknown`, `merge_state_unknown`, and a HEAD that cannot be read in step 9), or (with `--require-merged`) is not merged. The refusals it does not override: `not_a_worktree`, `not_a_git_repo`, `remove_main_checkout`, `default_branch_delete`, `option_invalid`, `base_not_found`, `base_not_remote_branch`, `head_moved` for a HEAD that can be read and is not at the listed commit (step 9), `git_timeout`, `interrupted`, and `worktree_remove_failed` (git itself failed, after the checks). |
| `--delete-branch` | Delete the worktree's branch after the worktree is gone, and only while it still points at the commit `git worktree list` showed before the checks (step 11). The removal refuses (`head_moved`, step 9) when the worktree's HEAD is no longer at that commit right before its first change, and a branch that gains a commit after that is kept, with a warning. |
| `--require-merged` | Refuse unless the branch is merged into `origin/<default branch>` (or the `--base` ref), by ancestry or by a merged pull request that `gh` reports as merged into the default branch (or the branch part of `--base`) at exactly the worktree's HEAD commit. Without `gh` a squash merge is not recognised: the state is unknown and the removal is refused (see [The merged rule](#the-merged-rule)). |
| `--base <rev>` | Run the merge check against a remote-tracking branch instead of origin's default branch, for a branch whose pull request targets another one (`origin/master` for a hotfix in a repository whose default branch is `develop`, say). `<rev>` is `<remote>/<branch>` or `refs/remotes/<remote>/<branch>` of a configured remote; it is resolved once, in the main checkout, to the full ref, and the check runs against that ref. The `gh` lookup uses the branch part after `<remote>/` as the pull request's base (`upstream/master` and `refs/remotes/origin/master` both give `master`) and runs against `gh`'s default repository: no `--repo` is passed, so the remote's own repository is not selected. Anything else (`HEAD`, `HEAD~1`, `@{u}`, rev syntax after a valid prefix such as `origin/x@{1}`, `origin/x~1`, `origin/x^` or `origin/x^{commit}`, a local branch, a sha, a tag, an option-like value, a remote's `HEAD`) is a `base_not_remote_branch` refusal, even with `--force`, because a verdict against a local or relative base must never excuse commits no remote has. A remote-tracking `<rev>` that does not exist is `base_not_found`. Both refuse before anything is removed. It only changes the merge check, so it needs `--require-merged` or `--delete-branch`: alone it is an `option_invalid` refusal, because a flag that silently changes nothing hides a mistake. The default-branch protection of `--delete-branch` still names origin's default branch. |
| `--sync-main` | After a successful removal, bring the main checkout up to date; see [Syncing the main checkout](#syncing-the-main-checkout). Without it nothing is fetched and the main checkout is not touched. |

### What it does

In this order, with every check that can refuse before the first change:

1. Resolves `<path>` and finds it among `git worktree list` entries.
2. Refuses the main checkout, and a locked entry without `--force`.
3. Nested worktree check: refuses when another registered worktree of the repository lies inside `<path>`, however its path is spelled, since `git worktree remove` would take that checkout and its uncommitted work with it. A prunable entry whose directory is gone does not count, since it has nothing inside to lose; a prunable entry whose directory is still there does.
4. Submodule check: refuses a work tree that has a `.gitmodules` file without `--force`, which is what git itself cannot remove either. The check runs before the links are unlinked, so nothing is half-changed.
5. Dirty check: `git status --porcelain --untracked-files=all`. Ignored paths are invisible here, which is what lets a worktree with its `.ai/run` pointer and its dependency links be removed without `--force`. A status that fails (non-zero, a git that could not start, or one that did not finish within its bound) is the `status_unknown` refusal, never a clean reading. Status does not compare a tracked file flagged assume-unchanged or skip-worktree with the work tree, so an edit to one would be deleted unseen, and neither does this check: it does not look at the content. It reads `git ls-files -s -v -z` (lowercase tag for assume-unchanged, `S` or `s` for skip-worktree) and refuses a worktree in which any flagged path is present in the work tree, edited or not, as `worktree_dirty`, naming the path and the flag (`<path> is flagged assume-unchanged`, listed in `details.flagged`); a file, a link, a directory or anything else `lstat` finds counts. A flagged path that is absent from the work tree, as a sparse checkout leaves it, has nothing to lose and does not count; nor does a submodule entry (mode 160000), which git never compares with the index. A listing that fails or does not finish, or a path that cannot be inspected, is the same refusal, never a clean reading. The way out is to clear the flag (`git update-index --no-assume-unchanged` or `--no-skip-worktree`) so that status shows the edit, or `--force`. Clean, for `remove` and `sweep`, means both: status shows nothing, and no flagged file is present in the work tree.
6. Merge check (only with `--require-merged` or `--delete-branch`): `git --no-replace-objects -c core.useReplaceRefs=false merge-base --is-ancestor HEAD refs/remotes/origin/<default>` (the full ref, or the `--base` ref; a grafted graph or a non-default `GIT_REPLACE_REF_BASE` makes the verdict `unknown` without asking, see step 7; messages and `merged.reason` show git's abbreviation of it, `origin/<default>` in a normal layout), and otherwise `gh pr list --state merged --head <branch> --base <default branch, or the branch part of --base> --json number,headRefOid,baseRefName`, where a merged pull request counts only when its `headRefOid` is the worktree's own commit and its `baseRefName` is that branch.
7. Unpushed check: `git for-each-ref refs/remotes` lists the symbolic refs under `refs/remotes`, and `git rev-list HEAD --not --exclude=<each symbolic ref> --remotes` counts the commits no remote branch has (for a reftable store both run in the common directory, from the commit the worktree's `HEAD` points at; see the reftable paragraph below). A symbolic ref does not count as a push, with or without `--base`: `git symbolic-ref refs/remotes/origin/self refs/heads/feat` would otherwise make the unpushed `feat` look pushed, and deleting the branch would leave its commits on no ref. A for-each-ref or rev-list that fails or does not finish within its bound is the `unpushed_state_unknown` refusal, never zero. A plain ref under `refs/remotes` still counts as a push, however it came there. A replaced or grafted commit graph is handled before any of that, because it changes what git counts as pushed without touching a ref: `git replace --graft <origin/main tip> <unpushed commit>` (or the same object installed with `git replace`, or a line in `info/grafts`) makes the unpushed commit an ancestor of a remote-tracking ref, so `rev-list` calls it pushed and `--delete-branch` would delete it. The calls that decide (the `rev-list` of this step, the `merge-base --is-ancestor` and the `rev-parse` of the HEAD commit in step 6) run with git's top-level `--no-replace-objects` option, `-c core.useReplaceRefs=false` and `-c core.commitGraph=false`, so the real commits are read whatever is in `refs/replace/`, and their parents are read from the commit objects and not from the commit-graph file. The replace settings are on the command line, and neither depends on the caller's environment: some git versions read a `core.useReplaceRefs=true` (from the repository or global configuration, `GIT_CONFIG_PARAMETERS` or `GIT_CONFIG_COUNT`) after the option and would turn replace refs back on, and a `-c` on the command line is applied after all of those. A `GIT_NO_REPLACE_OBJECTS` in the caller's environment and a `GIT_REPLACE_REF_BASE` that points at the replacements change nothing either. The third setting closes a second way to the same answer that touches no ref and no object: git keeps a parent list of its own in `objects/info/commit-graph` (and, for a split graph, below `objects/info/commit-graphs/`) and trusts it without comparing it to the commits, so a file in which a remote-tracking tip names the unpushed commit as its parent makes `rev-list HEAD --not --remotes` count 0 even with the replace settings. Writing such a file needs write access to the git directory. With `core.commitGraph=false` git ignores the file and reads each commit's parents from the commit object; like the replace setting it is a `-c` on the command line, so a `core.commitGraph=true` from the repository or global configuration, `GIT_CONFIG_PARAMETERS` or `GIT_CONFIG_COUNT` cannot turn the file back on. The cost is a walk without the graph's generation numbers and cached parents: git opens each commit object, so on a very large history the unpushed `rev-list` and the ancestry check are slower when the branch forks far below the remote tip. The calls keep their bounds, and a bound that passes is the same unknown state as for any other git call that does not finish. The option does not switch off grafts, so those are refused: an entry named `info/grafts` in the common git directory (any entry, even an empty file or a link; git reads the common directory's file, not the private directory of a linked worktree, and this check does the same), a `GIT_GRAFT_FILE` in the caller's environment (any value, `/dev/null` included), and a `GIT_REPLACE_REF_BASE` other than `refs/replace/` (the option already ignores those replacements; the refusal says the caller's git does not see the graph this check reads) are the `unpushed_state_unknown` refusal, and the merge check says `unknown` for them, so `--require-merged` reports `merge_state_unknown` and a merged verdict cannot excuse the commits. `list` reports the same `unknown` merge state for such a repository. git deprecates grafts but still reads `info/grafts` and `GIT_GRAFT_FILE` and prints a deprecation hint; a future git that stops reading them leaves the refusal in place. Before git is asked, the ref store git reads is inspected, and every input of that inspection is taken the way git takes it. The common directory is git's own answer to `rev-parse --git-common-dir`, kept as the bytes git printed with only the final newline taken off (a name that is not UTF-8, which a Linux file system allows, is never decoded into another name), and a relative answer is joined to the worktree path without folding `..`; a common directory that cannot be found is a refusal, not "no refs". Whether git keeps the store elsewhere is read from `<common-dir>/config` alone, the one file git's own repository-format reader reads: its bytes are handed to `git config --file - --no-includes`, so neither an included file nor `GIT_CONFIG`, `GIT_CONFIG_COUNT` or `GIT_CONFIG_PARAMETERS` in the caller's environment can hide or add an `extensions.refStorage` value (`GIT_CONFIG=/dev/null` hides the repository's `files://<path>` from an all-scope `git config`, while git keeps reading that store). Any value that is more than a bare format name (`files`, `reftable`), the same in `GIT_REF_STORAGE_FORMAT` or `GIT_REFERENCE_BACKEND` (newer git reads the first and keeps the second as an alias; two different values are refused too), and a `config` that cannot be inspected, read or parsed are refused, since no git command names that location. The backend is git's answer to `rev-parse --show-ref-format`; any answer other than exactly `reftable`, including that of an older git that does not know the option, is inspected as a files store. For a files store, `refs` must exist and be a real directory, and the whole `<common-dir>/refs` tree is walked with `lstat`, nothing followed or opened, every name listed and inspected as bytes: a file system symlink anywhere in it (`ln -s ../../heads/feat refs/remotes/origin/self`, `ln -s ../heads refs/remotes/mirror`, `refs/heads` or a directory below it such as `refs/heads/team` linked into `refs/remotes`, a link on `refs` itself, a link whose name is not UTF-8 beside a decoy named with U+FFFD), a directory reached a second time or lying on another device than `refs` (a bind mount, a mount point), a special file, an entry that cannot be inspected, or a tree past 500000 entries or 64 levels is the `unpushed_state_unknown` refusal, since git reads every path there as a ref and a local branch could read as a remote-tracking ref of itself. `<common-dir>/packed-refs` must be absent or a regular file: a link there, for example to an ignored file inside the worktree that the removal deletes, is refused too. For a reftable store, git opens `<common-dir>/reftable/tables.list` and every table it lists through whatever is there, so `reftable` must be a real directory, `tables.list` and every listed table a regular file (no link, no special file, nothing missing) on the device of `reftable`, every listed name a plain file name, and the list within 500000 entries; a table or `tables.list` linked to an ignored file inside the worktree, which the removal would delete with every ref in it, is refused. The remote-tracking refs git lists as symbolic are excluded by name; one whose name is not UTF-8 cannot be excluded exactly (a command argument is text) and is refused instead of letting `--remotes` follow it. In a reftable store a symbolic ref of the common stack whose name holds a non-ASCII character is excluded through a pure-ASCII pattern: every byte at or above 0x80 of the name becomes a `?`, because git converts a command-line argument to the composed form when `core.precomposeunicode` is on (macOS sets it at init) while a reftable record keeps the bytes it was written with, and an `--exclude` in the other form would match nothing and let `--remotes` follow the ref to the branch. A pure-ASCII argument is converted to itself on every platform, and wildmatch matches each `?` against the stored bytes one for one; a `?` can also match an ASCII byte, so the pattern may exclude one ref more than this name, which only ever keeps a branch. A plain (non-symbolic) remote-tracking ref with a non-ASCII name is not excluded and counts as a push as before, and the files backend is unchanged. The refusal names the first entry or setting it stopped at; `--force` removes anyway, as for every unknown state. Layouts that are refused this way although nothing aliases: a link made by `core.preferSymlinkRefs` (a deprecated setting), a `refs` directory, `packed-refs`, a reftable table or `tables.list` shared by linking it (as `git-new-workdir` does), a mount below `refs` or `reftable`, more than 500000 entries under `refs` or tables in the list, a repository without a `config` file, and, in a reftable store, a symbolic remote-tracking ref of the common stack to `HEAD` or to a ref under `refs/worktree/`, which the two listings resolve differently. A stray link in the `refs` directory of a reftable repository is ignored by git and by this check. A link inside a linked worktree's private git directory is not read by git for remote-tracking refs and not walked. A reftable repository differs in one respect: a linked worktree has a ref stack of its own, `<common-dir>/worktrees/<name>/reftable`, and git merges it into every ref listing made in that worktree, `refs/remotes/*` entries included, where the files backend never reads `worktrees/<name>/refs/remotes`. git writes remote-tracking refs (a push, a fetch, `git update-ref refs/remotes/...`) to the common stack even when it runs in a linked worktree, and only the worktree-private namespaces such as `refs/worktree/` and `HEAD` to the private one, so a table in the private stack that names a remote-tracking ref was not written by git. Read in the worktree, it would make `rev-list HEAD --not --remotes` count the commit it points at as pushed, and the removal deletes that stack and the ref with it. For a reftable store the walk therefore reads nothing of the private stack but the commit the worktree's `HEAD` points at: `git rev-parse --verify HEAD^{commit}` in the worktree names that commit (a `HEAD` that names no commit, as on an unborn branch, or an answer that is not an object name, is the `unpushed_state_unknown` refusal), the symbolic refs to exclude come from the listing of the common directory alone (`git --git-dir=<common-dir> for-each-ref refs/remotes`), and the walk runs there as well: `git --git-dir=<common-dir> rev-list <HEAD commit> --not --exclude=<each symbolic ref of that listing> --remotes`, with the replace-ref and commit-graph settings and the bound described above. A line of that listing whose symbolic ref target is not a ref name (`HEAD` or another name at the top level such as `FETCH_HEAD`, or a name below `refs/` that `git check-ref-format` accepts) is the `unpushed_state_unknown` refusal rather than a plain ref. The worktree's own listing is not used for the exclusions: for a record in the private stack that shadows a symbolic remote-tracking ref of the common stack, git can print a symbolic ref target there that is not the record's, an empty one included, and the walk would then follow the record. Before the walk, the listing `git for-each-ref refs/remotes` makes in the worktree (name, object name and symbolic ref target of each ref, symbolic ones included) is compared byte for byte with the listing of the common directory alone, and any difference, a ref the private stack adds, hides or re-points, is the `unpushed_state_unknown` refusal, as is a common directory whose name is not UTF-8 (it is passed to git as an argument) and one that holds an entry named `commondir` (any entry; git never writes one there, and with it `--git-dir=<common-dir>` reads another directory's refs as the common stack, so the comparison and the walk would be made against that). The comparison is a tripwire that fails closed, not a proof: since the target git prints in the worktree for a shadowing record is unreliable, two listings that agree do not show that the private stack holds no remote-tracking ref, which is why the walk does not read the worktree's refs. Nothing is left out of either listing before the comparison, symbolic refs included, so a symbolic remote-tracking ref in the common stack to `HEAD` (it resolves to the branch of the asking worktree) or to a ref under `refs/worktree/` (only the worktree that holds the target lists it) is a refusal as well, although nothing is forged; `--force` removes anyway. Not covered: a bind mount whose source lies outside `refs` or `reftable` (`lstat` cannot see it, and making one needs privileges), a change to the store between this check and the deletion, and a shallow repository (`shallow` in the common directory, or `GIT_SHALLOW_FILE`), whose boundary hides the history below it from `rev-list` as well. The commit graph itself is checked as described earlier in this step. A branch the merge check called merged is not refused here: its commits are named in `warnings` and treated as safe, so a squash-merged branch whose remote branch was deleted and pruned is removable without `--force` when `gh` reports its merged pull request at the worktree's commit. Without `gh` it is not merged as far as this command can tell, so `--delete-branch` refuses it as `unpushed_commits` and `--require-merged` as `merge_state_unknown`.
8. Branch guard: refuses to delete the branch the default base names, or the branch the main checkout is on.
9. A SIGINT or SIGTERM that arrived during the steps above ends the command here, with nothing changed (see [Time bounds](#time-bounds)). Then HEAD is read again (`git rev-parse --verify HEAD^{commit}` in the worktree, with the replace-ref and commit-graph settings of step 7): when it can be read and is no longer the commit `git worktree list` showed in step 1 (something committed, checked out or reset there while the checks ran), the removal refuses with `head_moved` and nothing is changed, with or without `--force`. When the listing showed no commit (an unborn branch, listed at the zero id) or HEAD names no commit that can be read now (an unborn branch, or a commit object that is missing), whether it moved cannot be told: without `--force` that is the same refusal, failing closed; with `--force` the removal goes on, as for any other check that cannot be made. This is the last read before the first change, so the commit removed is the one the listing showed and HEAD was at when the checks ended; a HEAD that was moved away and back while they ran is not seen. Otherwise it unlinks the ignored symlinks in the work tree (the dependency links `create` made), each with `unlink`, which removes the link itself and never follows it, so the shared directory in the main checkout is left exactly as it was.
10. `git worktree remove` from the main checkout (`--force` once, or twice for a locked entry, as git requires), then `git worktree prune`.
11. With `--delete-branch`: `git update-ref --no-deref -d refs/heads/<branch> <commit>`, where `<commit>` is the one `git worktree list` showed the worktree at in step 1, before any check ran. git compares and deletes in one step, so a commit made on the branch after the read in step 9 (in the worktree before step 10, or from anywhere else) makes the deletion fail: the branch is kept with that commit, `branch.deleted` is `false`, and a warning says where the branch points now. As `git branch -D` would, it keeps a branch that another worktree has checked out (`git worktree list` is read again for that) and, once the branch is deleted, removes its `branch.<name>` configuration (`git config --local --remove-section`), so that a branch made later under the same name does not inherit its upstream. The deletion cannot lose work in the normal path, because an unpushed branch was already refused in step 7 unless `--force` said otherwise or the merge verdict said the work is in the base.

Ignored files and directories inside the worktree (`.env`, build output, a real `node_modules`) are deleted with it, without `--force`, as `git worktree remove` does.

The main checkout is never modified by the removal itself: no `git stash`, `checkout`, `switch` or `reset` is run anywhere, and its HEAD, index, working tree and stash are untouched. (`--sync-main` is the one option that may fast-forward it, under the guards below; it never runs those commands either.) Only its administrative directories are written (`worktree remove`, `worktree prune`, and for the branch `update-ref -d` and `config --remove-section`). Removing a worktree never deletes its branch unless `--delete-branch` says so.

### The merged rule

Ancestry decides first (with `--base`, the base ref replaces `origin/<default branch>` here and the branch part of `--base` replaces the default branch below): `HEAD` is an ancestor of `refs/remotes/origin/<default branch>`, which covers a merge and a fast forward. A squash or a rebase merge leaves no ancestry, so `gh pr list --state merged --head <branch> --base <default branch> --json number,headRefOid,baseRefName` is asked next, and one merged pull request is a `yes` with `via: "gh"` only when it was merged into the default branch (`--base <default branch>`) at the worktree's HEAD commit, that is, its `headRefOid` is that commit and its `baseRefName` is the default branch. The commit has to match: a branch that gained commits after the merge, or whose name was reused for new work, is not covered by the pull request that merged an older head of it. The base has to match too: a pull request merged into another branch (a stacked pull request merged into its parent branch, say) says nothing about this base. `details.merged.reason` says so in both cases. `gh` is only consulted when it is installed and only when the answer is needed; when it is absent, or fails, or answers something that is not JSON, the verdict is `unknown`, and `--require-merged` reports `merge_state_unknown` rather than removing the worktree on a guess. `--force` is what overrides both a `no` and an `unknown`. The ancestry is read with `--no-replace-objects`, so a `git replace` that makes an unmerged branch an ancestor of the base changes nothing; a repository with a grafts file (`info/grafts`, `GIT_GRAFT_FILE`) or a non-default `GIT_REPLACE_REF_BASE` gets `unknown` without any of the calls above, in `list` as in `remove`.

Without `gh`, a squash or a rebase merge is not recognised: the verdict is `unknown`, `remove --require-merged` refuses with `merge_state_unknown`, and `sweep` skips the worktree with that reason. No rule reads the merge off the branch's content instead. Finding the branch's changes in the base does not show that no commit of the branch carries work the base lacks: commits made after the squash that add something and take it back, or that take over a change the base made since, leave the branch looking exactly like a merged one, and so does a branch stacked on a squash-merged branch, which carries its parent's changes. A merged pull request at the worktree's own commit does show it, because its head names exactly the commits that were merged, and any commit after it changes the tip.

A branch that is merged into the base, by ancestry or by a merged pull request at the same commit, holds no work the base does not have, so it is not counted as unpushed even when its own remote branch was deleted and pruned; those commits are named in `warnings` instead of stopping the removal.

### Syncing the main checkout

`--sync-main` collapses the chain that follows a merged pull request (remove the worktree, delete the branch, `git fetch --prune`, update the main checkout) into the one call. It runs only after the removal succeeded; a refused removal changes nothing, fetches nothing and has no `sync` field.

1. `git fetch --prune --no-prune-tags --no-recurse-submodules origin` in the main checkout (two-minute limit). `--no-prune-tags` keeps a `fetch.pruneTags` or `remote.origin.pruneTags` setting from deleting a tag only this repository has. A repository with no `origin` remote skips the whole step (`fetch: "skipped"`).
2. The fast-forward happens only when all of these hold, checked in this order; the first that fails is the `reason` of a `skipped` result and nothing is changed:
   - origin's default branch can be resolved;
   - no operation is in progress in the main checkout: none of `MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD`, `rebase-apply` (a rebase or a paused `git am`), `rebase-merge`, `sequencer` or `BISECT_LOG` exists where `git rev-parse --git-path` puts it;
   - the main checkout is on that branch (not another branch, not a detached HEAD);
   - `git status --porcelain --untracked-files=all` is empty: no staged, unstaged or untracked change;
   - the main checkout is not ahead of `origin/<default>` and has not diverged from it (a diverged or ahead checkout is reported with `ahead` and `behind`, and is never forced);
   - no file the fast-forward would add already exists in the work tree. Such a file is necessarily ignored by git, which a plain `merge` would overwrite without a word; this check only gives the clearer reason for it.
3. `git merge --ff-only --no-autostash --no-overwrite-ignore <refs/remotes/origin/<default>>`. With `--no-overwrite-ignore` git refuses to replace any ignored file or link in the way, also one at a parent path of a file the fast-forward adds (an ignored file `cfg` where the base adds `cfg/x`, or an ignored link there); that refusal is a `failed` sync with git's message, and the main checkout stays where it was. `checkout`, `switch`, `reset`, `stash`, `pull` and `--force` are never run.

`sync` in the result: `status` (`fast_forwarded`, `up_to_date`, `skipped`, `failed`), `reason`, `fetch` (`fetched`, `failed`, `skipped`), and when known `branch`, `base`, `ahead`, `behind`, and `from` and `to` (the main checkout's commits before and after a fast-forward). The exit code stays 0 whatever `sync` says, because the removal succeeded: a `failed` sync (the fetch or the merge itself failed, or a git call was cut off) adds a warning, a `skipped` one is an expected outcome that only `sync.reason` explains.

## sweep

```bash
agent-primitives worktree sweep --root ~/wt --dry-run
agent-primitives worktree sweep --root ~/wt
```

Removes, in one call, every linked worktree among the direct children of `--root` whose work is in origin's default branch, together with its local branch. Ignored files inside a removed worktree (`.env`, build output, the `.ai/run` pointer) are deleted with it, as with `remove`. It is a subcommand of its own rather than a `--merged` mode of `remove` because it has no `<path>`, takes none of `remove`'s per-worktree flags (`--force`, `--delete-branch`, `--require-merged`, `--base`) and returns a list with a different exit-code contract; `list --root` already sets the precedent for a directory-scoped command.

| Option | Meaning |
| --- | --- |
| `--root <dir>` | Required. The directory whose direct children are looked at, with the rules of `list --root` and two of its own: a child that is a symbolic link is not followed (it is a `skipped` entry, where `list --root` describes the work tree it points at), and an entry whose real path is not below the real `<dir>`, or is `<dir>` itself, is `skipped`, so nothing outside `<dir>` is removed. A child that is not a work tree top (a file, a plain directory, a subdirectory of a checkout) is passed over without an entry; a work tree that cannot be described (one of a bare repository, say) is a `skipped` entry. A worktree anywhere else (outside `<dir>`, or nested deeper) is never looked at. |
| `--dry-run` | Run every check and list what would be removed; nothing is changed. Each removable entry goes through `remove`'s own checks, stopping just before its first change, so a dry run refuses where the real run would (a submodule, a nested worktree, a branch the default base names, ...). It does not fetch: the verdicts rest on the remote-tracking refs as they are, so run `git fetch --prune origin` first (or `remove --sync-main` on the last worktree). |

An entry is removed only when all of these hold; otherwise it is `skipped` with the reason (and, when `remove` refused it, the refusal `reason` as `refusal`):

- it is a linked worktree, not a main checkout (a main checkout among the children is `ignored`: listed, never removed, and not counted as skipped);
- not prunable, not locked, and on a branch (a detached HEAD has no branch to delete with it);
- clean: `git status --porcelain --untracked-files=all` is empty and could be read, and no tracked file flagged assume-unchanged or skip-worktree is present in the work tree (step 5 under [remove](#remove); such a worktree is skipped with the refusal `worktree_dirty`, whether the file is edited or not);
- merged into origin's default branch by the shared merged rule above (`list`'s `merged: yes`: ancestry, or a merged pull request that `gh` reports at the branch's tip; without `gh` a squash-merged branch is skipped with the verdict's reason);
- not refused by `remove --require-merged --delete-branch`, which makes the same checks as above plus unpushed commits (commits no remote branch has are tolerated only because the merged verdict says the base has their work; they are named in the removal's warnings), nested worktrees and submodules, and never deletes the default branch or the branch the main checkout is on;
- the branch has commits of its own: its tip is not its fork point with the base (`git merge-base HEAD <base>` is not `HEAD`). Otherwise the entry is skipped with the refusal `no_own_commits`. A worktree created a moment ago, still holding the ignored files of a task in flight, has no commits of its own and is merged by ancestry, and a sweep cannot tell it from a branch merged by a merge commit or a fast forward, whose tip is an ancestor of the base too. So a sweep removes the branches whose squash or rebase merge `gh` reports at their tip, and leaves ancestry-merged ones to `worktree remove --require-merged --delete-branch`, which names the worktree. A fork point that cannot be read is the same refusal.

So "merged, clean and pushed" is: clean, and either all commits are on a remote or the base has the work. A branch with commits after its squash merge, pushed or not, is not merged and is skipped, and so is a branch stacked on a squash-merged one, which has no merged pull request of its own. The branch is deleted as `remove` deletes it (steps 9 and 11 under [remove](#remove)): a worktree whose HEAD is no longer the commit the listing showed, read right before the first change, is skipped with the refusal `head_moved`, and the branch is deleted only while it still points at that commit, so a branch that gained a commit after that read is kept, and the entry is `removed` with `branchDeleted: false` and a warning. There is no `--force` for a sweep.

### Result

The usual envelope with `command: "worktree sweep"`, plus `dryRun`, `root` (absolute), `summary` (`removed`, `wouldRemove`, `skipped`, `ignored`) and `entries`: first the children that were not described (symbolic links, work trees that could not be resolved), then one per work tree in `--root`'s sorted order. The top-level `warnings` carry those of `list --root` and every warning of each removal, prefixed with the entry's path:

| Field | Meaning |
| --- | --- |
| `path`, `repo`, `branch` | As in `list`; `repo` is absent for a child that was not described. |
| `action` | `removed`, `would_remove` (dry run), `skipped` or `ignored`. |
| `reason` | Why: what was removed, or the guard that held the entry back. |
| `refusal` | The `reason` code of the refusal when `remove` refused it. |
| `merged` | The merge verdict the decision rests on; absent for a child that was not described. |
| `branchDeleted` | For a removed entry: whether the local branch was deleted (`false` when it moved after the checks, another worktree has it checked out, or git failed; the entry's warnings say which). |
| `warnings` | For a `removed` or `would_remove` entry: the removal's own warnings (commits on no remote branch that the merged verdict excused, a link that could not be unlinked, a failed prune, a branch that was kept). |

Exit code and `status`: `0` and `ok` when nothing was skipped (including when nothing was found); `1` and `partial` when at least one entry was skipped (a worktree, a symbolic link, a child that could not be described) or a worktree was removed but its branch was kept, whether or not others were removed, so a caller reads `entries` for the details; `2` and `usage_error` for a refusal (`option_invalid` for a missing `--root` or one that is not a directory, `git_timeout`, ...). `ignored` entries never change the exit code. A per-entry refusal never aborts the sweep, except an interruption (SIGINT, SIGTERM), which ends the command at once; entries already removed stay removed.

## list

```bash
agent-primitives worktree list --repo ~/src/app
agent-primitives worktree list --root ~/wt
agent-primitives worktree list --repo ~/src/app --base origin/master
```

Read-only: no git command that writes is run. A git call that does not finish within its bound ends the report in the `git_timeout` refusal (no partial report), except the one inside the merge verdict, which leaves that entry's `merged` as `unknown` with the reason (see [Time bounds](#time-bounds)).

| Option | Meaning |
| --- | --- |
| `--repo <path>` | The repository to report: the main checkout, a subdirectory, or a linked worktree. Every worktree git lists is reported, main checkout first. Default: the invocation directory (`-C`). |
| `--root <dir>` | Instead of one repository, report the work trees that are direct children of `<dir>`, sorted by name. A child that is not a work tree top (a plain directory, or a subdirectory of some checkout) is skipped silently. A child that is a work tree but whose repository cannot be described (a work tree of a bare repository, say) is left out with a `skipped <path>` warning, and its siblings are still reported. A child whose git did not answer in time is not skipped: that is the `git_timeout` refusal for the whole report, since a skipped child would read as a complete listing. Exclusive with `--repo`: both together are an `option_invalid` refusal. |
| `--base <rev>` | Measure `ahead`, `behind` and `merged` against a remote-tracking branch instead of origin's default branch (`origin/master` for hotfix branches in a repository whose default branch is `develop`, say); each entry's `base` shows `<rev>` as given. `<rev>` is `<remote>/<branch>` or `refs/remotes/<remote>/<branch>`; it is resolved once per repository, in its main checkout, to the full ref, and every worktree is measured against that ref. A value that is no exact remote-tracking ref name (`HEAD`, `HEAD~1`, `origin/x@{1}`, `origin/x^`, a local branch, a sha, a tag) is a `base_not_remote_branch` refusal. Without `--root`, a well-formed `<rev>` whose ref does not exist in the repository gives every entry `merged: unknown` with a reason, null `ahead`/`behind`, and one warning (exit 0), while a value that is no remote-tracking branch at all is the `base_not_remote_branch` refusal. With `--root` the flag applies to every repository. A value that can never be a remote-tracking branch in any repository (empty, starting with `-`, `HEAD`, a sha or any value without a `<remote>/<branch>` shape, `<name>/HEAD`, rev syntax) is refused up front as `base_not_remote_branch`, before any repository is read. A repository where `<rev>` names a remote that is not configured, or a ref that does not exist, gives that repository's entries `merged: unknown` with a reason, null `ahead`/`behind`, and one warning; the report still completes. The `gh` lookup uses the branch part after `<remote>/` as the pull request's base and runs against `gh`'s default repository: no `--repo` is passed, so the remote's own repository is not selected. Still read-only: nothing is fetched, so a remote-tracking `<rev>` is as fresh as the last fetch. |

Per entry:

| Field | Meaning |
| --- | --- |
| `path`, `repo`, `main` | The directory, the basename of the main checkout it belongs to, and whether this entry is that main checkout (the only `main: true` of a repository). |
| `branch`, `head` | From `git worktree list --porcelain`; `branch` is absent for a detached HEAD. |
| `base` | The base the three fields below are measured against: the `--base` value, or else the default base (`origin/main`, say; `remotes/origin/main` where a local branch or tag called `origin/main` exists), absent when no default can be resolved. |
| `runPointer` | Trimmed content of `<path>/.ai/run`, `null` when absent. |
| `dirty` | Whether `git status --porcelain --untracked-files=all` says anything, `null` when git could not answer. |
| `ahead`, `behind` | `git rev-list --left-right --count <base>...HEAD`: commits only on `HEAD`, and commits only on the base. `null` when either could not be told. |
| `merged` | The same verdict as `remove --require-merged` would reach (`via` is `ancestry`, `gh` or `none`). `merged: yes` means the branch's work is in the base; `remove` still checks dirty and unpushed state. A git or `gh` call that did not finish in time makes it `unknown`, with the reason. |
| `links` | The ignored symlinks in the work tree: the dependency links `create` made. |
| `prunable`, `locked` | git's own flags for the entry. |

A prunable entry has no work tree git can read, so `dirty`, `ahead` and `behind` are `null`, `links` and `runPointer` are empty, and `merged` says why: `prunable: the directory is gone` when it is, and `prunable: the directory still exists but git no longer treats it as a worktree` (with git's own reason when it printed one) when only the `.git` file inside it is missing or points elsewhere. In the second case the directory may hold work: look at it before running `git worktree prune`.

## Time bounds

Every git call of `create`, `remove` and `list` has a hard time bound, so that a repository git cannot read (a fifo among the refs, which some git versions block on, or a hook, filter or credential helper waiting for input) ends the command in a refusal instead of hanging it. The bounds are generous, so that a large repository on a slow disk is not refused for being slow:

| Calls | Bound |
| --- | --- |
| Reads of refs, config or one object (`rev-parse`, `show-ref`, `for-each-ref`, `remote`, `symbolic-ref`, `check-ref-format`, `check-ignore`, `config`, `worktree list`) | 5 minutes |
| Small writes (`worktree prune`, and for the branch `update-ref -d` and `config --remove-section`) | 5 minutes |
| Walks of a whole work tree or the history, and calls that write one (`status`, `ls-files`, `rev-list`, `merge-base`, `worktree add`, `worktree remove`) | 30 minutes |
| `git fetch origin` | 2 minutes |
| `gh pr list` of the merge verdict | 30 seconds |

When a bound passes, the git call is killed with SIGKILL together with every process it started: git runs in a process group of its own and the whole group is killed, so a `ssh`, hook or filter that git started does not outlive the command. (On Windows git gets no process group of its own and only git itself is stopped at the bound.)

Because git runs in a session of its own, a prompt it would put on the terminal (an ssh passphrase, a host key question) fails at once instead of waiting for an answer, and no signal sent to the CLI's process group reaches it. What that means for interrupting the command:

- Ctrl-C (SIGINT) and SIGTERM sent to the CLI cannot be handled while a git call runs: the CLI waits for git, and git does not see the signal. `remove` and `create` handle a signal that arrived during their checks before their first change (`remove` before it unlinks the first link, `create` before the fetch and again before `git worktree add`): the command ends there with exit 130 (SIGINT) or 143 (SIGTERM) and no output, as every command of this CLI does on these signals, and nothing was removed or created (a fetch that already ran has updated the remote-tracking refs, as it has before any later refusal). A signal that arrives after that point lets the command run to its end; it then exits with its result, or with 130 or 143 and no output when the signal is handled before the result is written. `list` changes nothing and runs to its end. A program that calls `removeWorktree` or `createWorktree` itself and passes an aborted `signal` gets the `interrupted` refusal at the same points.
- SIGKILL and SIGHUP end the CLI at once (a harness timeout, `timeout -s KILL`, a closed terminal), and git does not outlive it: git is started through a small `/bin/sh` wrapper that also runs a watcher in git's group. The watcher waits on a pipe whose other end the CLI holds and never writes to. The kernel closes that end when the CLI dies, also when nothing reaps the dead CLI (a container whose first process does not reap, a parent that never waits for it), and the watcher then kills the group. The wrapper passes git's exit status, stdin, stdout and stderr through unchanged, gives git no copy of the pipe, and adds only the variables a shell sets (`PWD`, `SHLVL`, `_`) to git's environment; it runs git past a shell function of that name exported in the environment, switches off for itself the shell options an exported `SHELLOPTS` turns on (git still gets the variable; with `verbose` the wrapper's first line is printed before it runs and so still reaches git's stderr, while stdout and the exit status stay git's own; a `SHELLOPTS` with `noexec` makes a bash `/bin/sh` run nothing at all, which no wrapper can undo), and costs a few milliseconds per call. A git that a signal ends is reported with the shell's status for it (128 plus the signal number), and what it started is killed with its group. Without `/bin/sh` (Windows) there is no wrapper and no watcher.
- Not covered: a git that has exited while a process it started still holds its output. The CLI waits for that process until the bound, which kills it; when the CLI itself is killed in that window, the watcher has already stopped with git, and that process runs on until it ends by itself.

A call that did not finish is never read as an answer. Before the first change it is a refusal: `git_timeout` for the calls whose result would otherwise be taken as "no such ref", "no origin" or an empty listing, and the existing reasons where a check already has one (`status_unknown`, `unpushed_state_unknown`, `merge_state_unknown`, `fetch_failed`, `worktree_add_failed`, `worktree_remove_failed`). `--force` overrides the `status_unknown`, `unpushed_state_unknown` and `merge_state_unknown` readings as it does any other failure of those checks, and nothing else. After the first change nothing can refuse any more, so a call that did not finish is reported instead: a warning in `create` (the head, the upstream, the pointer and the link manifest are then reported as what could not be read), and `pruned: false` or `branch.deleted: false` with the reason in `remove`.

A git killed this way gets no chance to clean up, so a lock file or a partly written state can remain in the repository after any call that writes: `git worktree add`, `git fetch`, `git worktree remove`, `git worktree prune` and the branch deletion (`git update-ref -d`, `git config --remove-section`). The `worktree_add_failed` and `worktree_remove_failed` refusals say so; after a stopped fetch, prune or branch deletion, look for `*.lock` files in the repository before trying again.

The bounds are constants, not options. The environment variable `AGENT_PRIMITIVES_WORKTREE_GIT_BOUND_MS` exists for tests: a positive integer number of milliseconds that shortens every bound to at most that value; a value at or above a bound, or anything that is not a positive integer, changes nothing, so it can make the commands refuse sooner but never wait longer. A repository whose single git call legitimately needs longer than 30 minutes is outside what these commands are meant for; run git there directly.

## Related

`worktree create` writes what `worktree remove` later cleans up: the branch, the `.ai/run` pointer and the dependency links are its three artifacts, and `remove` reports the branch it deleted and each link it unlinked. `list` reads the same fields back, so `create`'s envelope, `list`'s report and `remove`'s report describe one worktree in the same terms.
